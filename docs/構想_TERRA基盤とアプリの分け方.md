# 構想：TERRAの基盤・事務所・現場アプリの分け方

> **正本は `kfrsj149-ai/terra-common`（architecture/TERRAの全体像.md）。** このファイルはコピー。内容が食い違うときは terra-common を正とする（2026-10-02〜）。

> 2026-10-02 神田さんとの議論の記録。**構想であり、まだ実装していない**（決まったことは「決定」と書いた）。
> 対象：SATEI-RA（査定・値付け）／SHIN-RA（経営ダッシュボード）／NIPPO-RA（日報・点検・免税軽油）／LOG-RA（検収。このアプリ）。
> 事務所端末（`/office/`）は、検収アプリの付属ではなく、**TERRA全体の「事務所」の土台**として育てる。

---

## 結論

| 層 | 置くもの | 形 |
| --- | --- | --- |
| **基盤**（サーバー1つ） | 事業体・契約・権限、**現場の台帳**、**単価表**、車番・納入先・樹種などのマスター、納入枠、お知らせ・指示 | アプリに属さない共通のAPIとデータ |
| **事務所**（PC中心・1か所） | 台帳・単価の管理、納入枠、お知らせ、便の確認、**経営ダッシュボード（SHIN-RA）** | 「TERRA 事務所」1つ。SHIN-RAは、その中の「経営」の画面（課金で解禁） |
| **現場アプリ**（スマホ・圏外で動く） | 目的別に分ける：検収（LOG-RA）／日報・点検・免税軽油（NIPPO-RA）／査定（SATEI-RA） | それぞれ独立したPWA。使う人の仕事に合うものだけを入れる |

**「どれで何をするんだっけ」は、現場では「仕事ごとにアプリが1つ」、事務所では「場所が1つ」で解決する。**

## 1. PWAの中にPWAは入れられるか

**入れられない。** PWAは「1つのWebサイト＋1つのマニフェスト」で、入れ子にはできない。
iframeで別のサイトを埋め込むことは技術的にはできるが、現場アプリでは避ける：

- 保存領域・Service Workerの範囲が分かれて、圏外で動かない／重複する
- 画面が消えない設定（Wake Lock）・カメラ・位置情報などの許可が、埋め込み先で効かないことがある
- 更新のたびに、親と子の版の組み合わせが壊れうる

代わりにできること：
- **同じアプリの中に「画面（モジュール）」として入れる**（契約に応じて表示を出し分ける）
- 現場アプリから、**「経営ダッシュボードを開く」ボタンで、事務所のWebを別のタブで開く**（契約がなければ案内を出す）。これで十分で、入れ子は要らない

## 2. 1つのアプリにまとめるか、分けるか

**現場アプリは分ける。事務所は1つにまとめる。** 理由：

1. **使う人と仕事が違う。** 検収員・運転手（LOG-RA）／作業員・オペレーター（NIPPO-RA）／査定する人（SATEI-RA）は別の人で、別の場所で、別の入力をする。
   全部入りにすると、手袋・炎天下で使う画面に、その人に要らない機能が並ぶ（「ゼロ負担入力」に反する）
2. **失敗を巻き込まない。** LOG-RAは売上の中心で、現場で使っている最中。SHIN-RAの不具合で検収が止まる構造にしない
3. **売り方が違う。** LOG-RAは「検収アプリ 年9,800円」で単独で入口になる。別の会社が「機械は要らないが検収だけ欲しい」と言える
4. **起動が速い。** 現場アプリは小さく保てる

まとめたほうがよいもの：
- **NIPPO-RA = 日報＋機械点検＋免税軽油**（すでに統合する決定。同じ機械QRから入る同じ人の作業だから）
- **事務所**：台帳・単価・納入枠・お知らせ・便の確認・経営ダッシュボード。事務員と経営者は別の人だが、**同じ場所**に入って、権限で見える範囲を変える

**「一体型（1つのPWAを契約で解禁）」が向く条件：** 同じ人が2つ以上の現場アプリを毎日使うようになったとき。
そのときは、現場アプリの殻を共通化し、モジュールとして束ねる。**いまは必要ない**（検収と日報は、使う人が別）。

### 契約（課金）の持ち方
- Stripeの契約は**事業体ごとに1つ**にして、中身（商品）で、どのアプリ・どの画面が使えるかを決める
- ライセンスコードが事業体と、使える商品の一覧を表す（いまは「検収の年額」だけ。商品を増やす形に拡張する）
- 契約のないアプリ・画面は、**開けるが「契約が必要です」と案内する**（現場で突然止まらないよう、既存の猶予の仕組みを踏襲）

### ドメイン（QRと同じく、決めたら動かさない）
| 用途 | 例 |
| --- | --- |
| QR・ハブ | `terra-tx-jp.com/m/…` |
| 事務所・経営（SHIN-RA） | `office.terra-tx-jp.com` |
| 基盤のAPI | `api.terra-tx-jp.com` |
| 現場アプリ | `kennsyuu.` / `nippo.` / `satei.`（アプリごとに分けると、キャッシュ・保存領域が混ざらない） |

**未決定。** 他のアプリに基盤のAPIを読ませる前に決める（共通ルール_現場名とID.md 参照）。

## 3. 現場IDは誰が発行するか（導入順への答え）

導入の順番は、SATEI-RA → SHIN-RA → NIPPO-RA → LOG-RA の順に「先に入れる事業体」がありうる（入口はまちまち）。

**決定：IDの発行は、どのアプリでもなく「基盤のサーバー」が行う。** 導入順は関係ない。
- 最初に入れたアプリが何であっても、現場を作る操作は「事務所」の機能（またはその事務所の権限）で、サーバーがIDを発行する
- 後から入れたアプリは、すでにある台帳を読むだけ（`feed`）。IDの付け直しも、台帳の作り直しもない
- そのため、**事務所端末（いまの `/office/`）は、LOG-RAに付属するのでなく、基盤の最初の窓口**になる

### 現場の「段階」（未実装・提案）
SATEI-RAは「まだ買っていない山」を扱うので、台帳の現場に**段階**を持たせる：

候補（査定中）→ 確定（購入・契約）→ 施業中（日報・検収が始まる）→ 完了 ／ 見送り

- IDは**候補の時点で発行**し、最後まで同じIDで通す（査定の記録が、そのまま日報・検収・経営分析につながる）
- いまの台帳の「完了」（`closed`）は、この段階の1つにあたる。拡張するときは、`closed` を `stage` に置き換える（移行は読み込み時に変換）
- **単位の注意：** 査定の「山林（物件）」と、作業の「現場」は、同じ単位とは限らない（1つの山林を複数の現場に分けて作業することがある）。
  必要になったら、現場に `parentId`（山林）を持たせる。**先回りして作らない**

### 現場の端末が、圏外で新しい現場を作る場合（SATEI-RAで起きる）
査定の人は、山で新しい現場を見つける。圏外では、サーバーがIDを発行できない。
→ 端末は**仮のID**（`tmp-…`）で記録し、通信できたときサーバーが本物のIDを発行して、**仮IDを本物に置き換える**（記録側のIDも置き換える）。
**現場の台帳ルール「端末はIDを発行しない」の例外ではなく、「仮のIDは本物のIDではない」という扱い。** 設計は、SATEI-RAを作るときに行う。

## 4. 単価はどこに置くか

**基盤の共通マスター（事務所で編集する「単価表」）に置く。SHIN-RAの中ではない。**

理由：
- 単価を使うのは、SATEI-RA（査定・値付け）、LOG-RA（概算金額）、SHIN-RA（損益）と複数。SHIN-RAの中に置くと、**SHIN-RAを入れていない事業体が、査定にも検収にも使えない**
- SHIN-RAは、基盤のデータ（単価・便・日報・査定）を**読んで分析する側**。データの持ち主にはならない

単価表の形（案）：
- 工場 × 樹種 × 規格（長さ・径級の範囲）× 区分（A材・B材・C材など）→ 単価（円/m³）
- **適用開始日つき**で履歴を持つ（改定しても、過去の便の金額が変わらないように）
- 金額は便に保存せず、**表示・集計のときに、その日の単価で計算**する（最終は精算書の値。見込みと確定の区別は納入枠と同じ）

### ⚠ 単価・原価は事業の機密
いまの運営者の閲覧・匿名化の同意は、**検収データ**を範囲にしている。**単価・原価・損益は、これに含めない。**
経営データ（単価・原価・損益）を運営者が見る・使うなら、**別の同意文・別の版**で、別に同意を取る。何もしなければ、運営者は見られない設計にする。

## 5. 増材指示（優先して取る材の指示）はどこに置くか

例：「カラマツの末口32cm以上は単価が高いので優先して取る」「工場から○○が足りないと言われているので、それを優先する」

**置き場所：事務所で書き、日報（NIPPO-RA）の画面に出す。** 検収（LOG-RA）にも出せる。
- 見るのは作業員（日報の入力前に目に入る）。**見る場所に出す**のが大事
- 事務所の「お知らせ」と同じ仕組み（期限つきのカード）に、種類「優先材の指示」を足す形が最も小さい
  - 項目：樹種・長さ・径級の下限・優先する理由（単価が高い／工場が不足）・期間・数量の目安（任意）
- **将来：** 単価表と納入枠の残りから、優先度を**自動で提案**する（「カラマツ32cm以上は、単価が他より15%高く、枠が残っています」）。人が確認して出す

先に決めた「配車・出荷の指示は作らない（電話で済む）」とは別物：
- 配車は一回きりで、電話で済む
- 増材指示は、**繰り返し・損得に直結・毎日の作業に影響**する。アプリにする価値がある条件（繰り返す／間違えると損／記録が要る）に合う

## 6. 事務所端末でできるとよいこと（優先順）

| 順 | 内容 | 理由 |
| --- | --- | --- |
| 1 | **車番・納入先・樹種のマスターを事務所から配る**（現場台帳と同じ仕組み） | いまは端末ごとに手入力で、表記ゆれが出る。運転手の入力が減り、工場名が揃うと納入枠の消化も自動で合う |
| 2 | **工場の検収値との差の分析**（工場別・樹種別の差の率） | すでにデータがある。規格外のはね・測り直しの傾向が分かり、工場との交渉材料になる |
| 3 | **納入枠のペース予測**（このペースだと月末に○m³余る／足りない） | カウントダウンの次に欲しくなる |
| 4 | **データの持ち出し**（全データのCSV/一式ダウンロード） | 解約時・不安時の安心。信頼につながり、実装も小さい |
| 5 | **事務所のアカウントを個人ごとに**（事務員・経理は閲覧のみ、など。操作者の記録つき） | いまは事務所コード1つの共有。誰が何を直したかが残らない |
| 6 | **単価表と概算金額**（便ごと・納入先ごと） | 単価の置き場所が決まったので。精算書との突合の前段 |
| 7 | **優先材の指示カード** | 日報側ができてから |
| 8 | 運送会社別の便数・材積の集計 | 運賃精算の根拠。外注運送会社への配信と一緒に |
| 後 | 外注運送会社への配信／精算書の取り込み（OCRは最後） | 利用者が付いて、実物を見てから |

## 決めたこと（2026-10-02）
1. 現場アプリは目的別に分ける。事務所は1つに統合する。SHIN-RAは事務所の「経営」の画面（課金で解禁）
2. PWAの入れ子はしない。現場アプリからは「事務所を別のタブで開く」ボタンにする
3. **現場IDの発行は基盤のサーバー。導入順に依存しない。** 現場に段階（候補→確定→施業中→完了／見送り）を持たせる（実装はSATEI-RAのとき）
4. 単価は基盤の共通マスター（適用開始日つき）。経営データ（単価・原価・損益）は、運営者の閲覧・匿名化の同意に含めない（別に同意を取る）
5. 増材指示は、事務所で書き、日報に出す（お知らせの仕組みの種類を足す）
