# TERRA共通QR規格

> 2026-10-01 決定。丸太検収・免税軽油・林業アカデミー・日報・点検整備、すべてのTERRAアプリで守る。
> 他プロジェクトのセッションには、このファイルの内容をそのまま渡すこと。

---

## 結論（1行）

**重機・車両1台につきQRは1つ。中身は「その機械のID」だけ。どのアプリを開くかは、読んだ後に選ぶ。**

---

## 規格

### URLの形

```
https://terra-tx-jp.com/m/7K3QX9AB
                       │  └─ 機械ID（8文字）
                       └─ 種別（m = 機械・車両）
```

| 部分 | 決め事 |
| --- | --- |
| ドメイン | **TERRA TXが恒久的に持つドメイン**（`terra-tx-jp.com`）。`vercel.app` は使わない |
| 種別 | `m` = 機械・車両（重機、トラックなど）。下の予約を参照 |
| ID | **8文字。意味を持たせない**（ランダム）。文字は `0123456789ABCDEFGHJKMNPQRSTVWXYZ`（紛らわしい I L O U を除く） |
| アプリ名 | **QRに入れない**。入れるとアプリごとにQRが要り、「1台1QR」が崩れる |
| クエリ（`?…`） | **付けない**。付けてよいのは将来の使い捨てQR（椪の杭など）だけ |

### 種別の予約

| 種別 | 用途 | 状態 |
| --- | --- | --- |
| `m` | 機械・車両（重機、トラック） | **確定** |
| `c` | 会社（検収の納品書に刷るQR） | 確定（丸太検収。構想段階） |
| `l` | 椪・ロット（山土場の杭） | **予約のみ。未決定** |

### IDの発行

- IDは**事務所がオンラインで機械を登録した時に、サーバーが発行する**。これで重複が起きない
- 機械を登録するのは最初の1回だけ。以後の運用は圏外でよい
- ナンバーや持ち主が変わっても**IDは変えない**（QRを貼り替えなくて済む）

### 刷り方・貼り方

| 項目 | 決め事 |
| --- | --- |
| 誤り訂正 | **H（30%まで欠けても読める）**。泥・粉塵・擦れを前提にする |
| 大きさ | 10〜15cm角（短いURLなので33マス。マスが大きく刷れる） |
| 余白 | QRの周囲に**4マス分の白**。余白も部品のうち |
| 色 | 濃い色×薄い背景なら何色でもよい。**黒か濃い緑**が退色に強い。赤・黄は先に飛ぶ |
| 仕上げ | **マット**。光沢は日光で白飛びする。反射材は使わない |
| 人が読める文字 | **QRの下にIDを必ず印刷する**（`7K3Q-X9AB` のように区切る）。読めない時の最後の手段になる |
| 土台 | 白いプレートの上に刷る。車体がデコトラでも読める |

## 絶対ルール（この3つは破らない）

**① QRには「変わらないもの」だけを入れる。**
機械の持ち主・現場・樹種・日付のように変わるものを入れると、変わるたびに刷り直しになる。
実測でも、日本語入りの長いURL（106バイト）は53マス、短いIDだけ（34バイト）は33マス。
**情報を詰めるほどマスが小さくなり、汚れに弱くなる。**

**② QRを読んでも、他人には何も見えない。**
QRは機械に貼ってあるので誰でも読める。IDだけを入れておき、
中身は**その機械を登録した端末にだけ**出す。見知らぬ端末には「未登録の機械です」と出すだけ。

**③ QRのURLは永久に使う。**
機械には何年も貼りっぱなしになる。**あとからドメインを変えると全部の機械で読めなくなる。**
裏側のサーバーや各アプリの場所は変えてよいが、QRのURLだけは変えない。

## 読んだらどうなるか

```
カメラで読む
   ↓
terra-tx-jp.com/m/7K3QX9AB が開く（ハブ）
   ↓
その端末が知っている機械なら、アプリの選択画面
   ┌──────────────────────┐
   │ ○○号機（PC200）                  │
   │ [ 日報 ]  [ 点検 ]  [ 給油 ]     │ ← 大きなボタン。使う順に並べる
   └──────────────────────┘
   ↓
選んだアプリが、機械を選択済みの状態で開く
```

- 手袋でも押せる大きさにする。**1タップで目的のアプリに入る**
- よく使うアプリを覚えて先頭に並べる
- 未登録の端末には何も見せない（絶対ルール②）

## 前提と、まだ決まっていないこと

実装に入る前に、次を決める必要がある。**ここが本当の難所。**

### 1. 各アプリの置き場所（要判断）

現在、各アプリは別々のドメインにある（丸太検収は `terra-kennsyuu-app.vercel.app`）。
QRのURLは永久に使うので、**QRに刷るドメインは自前のもの**にする（絶対ルール③）。
アプリ本体の置き場所は2通りある。

| 案 | 例 | 特徴 |
| --- | --- | --- |
| 別々のサブドメイン | `kennsyuu.terra-tx-jp.com` | Vercelの設定とDNS1行で足せる。**キャッシュ・DB・Service Workerが完全に別**になり、互いを壊さない |
| 同じドメインのパス | `terra-tx-jp.com/kennsyuu/` | 入口を1つにまとめやすい。ただしキャッシュ・DB・SWが同居し、互いを壊しうる（下記） |

**圏外で別アプリへ移れるかどうかは、置き場所では決まらない。**
その端末で一度オンラインで開いて保存済みなら、別ドメインのアプリでも圏外で開ける。
これは「導入時にオンラインで1回開く」という前提と同じ条件である。
（※ 2026-10-01 に訂正。当初は「別ドメインは圏外で開けない」と書いたが誤りだった）

**同じドメインに置くと、次の事故が起きる。丸太検収のコードで確認済み。**

- `sw.js` の `activate` が「自分の名前でないキャッシュを全部消す」作りになっている
  → 同じドメインの別アプリが作ったキャッシュを**消してしまう**
- `src/js/updater.js` の更新処理が `caches.keys()` の**全部**を消す
  → 同じく、別アプリのキャッシュを巻き込む
- IndexedDBの名前が重なると、別アプリのデータを読み書きしてしまう

→ **キャッシュ名とDB名に、アプリごとの接頭辞を付けて、自分の接頭辞のものだけ触る**ようにする。
　 同じドメインに寄せる前に、必ず直す。

### 2. 機械台帳をどこに置くか（要判断）

免税軽油は、アワーメーターの機械ごとに記録している。
日報も点検も機械が要る。**各アプリが別々に機械の一覧を持っているはず。**
（他アプリの中身は、このセッションからは見えていない。要確認）

QRのIDと、各アプリの機械をどう結びつけるか。

| 案 | 中身 | 向き不向き |
| --- | --- | --- |
| A. 共通の機械台帳をサーバーに置く | 事務所が一度登録。各アプリが同じ台帳を見る | 一貫するが、サーバーと認証が要る。圏外の初回登録に弱い |
| B. 各アプリが自分の機械一覧を持ち、**初めて読んだ時に1回だけ紐づける** | 「この機械は、どの○○号機ですか？」と選ぶ | サーバー不要・圏外で動く。ただし機械ごとに各アプリで1回ずつ手間 |

**最初はBが現実的**（既存アプリを壊さず、サーバーも増えない）。
機械の数が増えて手間が目立ってきたらAへ移行する。**まだ決めていない。**

### 3. 同じトラックQRを、工場が読む場合（検収側の構想）

丸太検収の構想では、トラックのQRを**工場が読んで、載っている荷を見る**。
同じQRを、持ち主が読めば「アプリ選択」、工場が読めば「荷の受領」になる。
**読む人によって出し分ける**ことになる。設計は構想メモ（`docs/構想_検収データを工場へ渡す.md`）で詰める。

### 4. 各アプリの、すでにあるQRの中身

免税軽油・林業アカデミー・日報で、すでにQRを使っている。
**書式がこの規格と違う可能性が高い。** 各アプリ側のセッションで現状を確認し、差し替える。

## 調査結果を受けた見直し案（2026-10-01・**案。神田さんの確認待ち**）

免税軽油と日報（NIPPO-RA）の報告
（`docs/報告_免税軽油PWAの現状.md`、`docs/報告_日報PWAの現状.md`）を受けて、
「前提と未決定」を見直す。**報告の文章からの推測を含む。各アプリのClaudeに確認する。**

> ※ 同日、免税軽油の報告だけを見て「日報・点検は免税軽油に足す」と書いたが、
> 日報の報告で**撤回した**。日報はすでに別のアプリとして存在し、技術・DB・利用者の持ち方が違っていた。

### 分かったこと

| | 免税軽油 | 日報（NIPPO-RA） | 点検 | 検収 |
| --- | --- | --- | --- | --- |
| 技術 | React/TS（ビルドあり） | 素のJS＋esbuild | 未作成 | 素のJS・サーバーなし |
| サーバー | Firebase（プロジェクトA） | Firebase（プロジェクトB） | — | なし（決済確認だけVercel Functions） |
| 利用者の持ち方 | 複数の会社（会社ごとに分離） | **単一**（会社は `TERRA` 固定） | — | 端末内 |
| 課金 | Stripe | なし | — | Stripe |
| 機械台帳 | あり（Firestore自動ID） | あり（自動ID。**別のDB**） | — | なし |
| アワーメーター | あり（給油ごと） | **なし**（午前／午後／全日の3択） | — | — |
| QR | あり（印刷機能も実装済み） | なし（構想メモのみ） | — | なし |
| 権限 | 事務所と現場端末で分かれる | **フラット**（許可済みなら誰でも読める） | — | — |

2つのアプリは別々のFirebaseにあり、**同じ機械が2か所に別のIDで登録されている。共通のキーがない。**

### 見直した方針（案）

1. **機械まわりは、アプリを統合しない。** 日報は別のアプリとして存在し、足し込むと作り直しになる。
   また日報はアワーメーターを使っておらず、統合の根拠にしていた「数字の共有」は今は成り立たない
2. **QRを入口にして束ねる。** `https://m.terra-tx-jp.com/<ID>` を、ボタンだけの小さな静的ページ（ハブ）にする。
   ハブは機械のデータを持たず、押された先のアプリへIDを渡すだけ（絶対ルール②は守られる）
3. **QRのIDが、各アプリの機械をつなぐ共通の背番号になる。** 各アプリは自分の機械に「QRのID」の欄を持つ。
   最初に読んだ時に1回だけ「この機械はどれですか？」と紐づける（サーバーの共有は要らない）。
   IDの発行は、QR印刷機能を持つ免税軽油で行うのが自然
4. **別々のサブドメイン・別々のFirebaseのままでよい。** キャッシュ衝突は起きない
5. **既存のQR（免税軽油の `/scan?machine_id=…`）は壊さない。** 古い形式は読めるまま残す
6. **点検の置き場所は未決定。** 日報は権限がフラットで、点検に必要な
   「個人の責任記録」「異常時の連絡」に足りない。
   アワーメーター（何時間ごとの整備）が使え、権限を細かくできる免税軽油側が有力（案）

### 決めるべきこと（神田さんへ）

- 日報は、売る予定か、社内用か（売るなら、複数の会社への対応・課金・権限が要る）
- 免税軽油のQRは、すでに機械に貼って使っているか。何台か
- QRの宛先を `m.terra-tx-jp.com` にしてよいか（**QRのURLは一方通行。刷ったら変えられない**）

## 各アプリへの指示（そのまま貼る用）

> TERRA共通のQR規格が決まった。このアプリでQRを使う場合は、次に従うこと。
>
> 1. 機械・車両のQRは `https://terra-tx-jp.com/m/<ID8文字>` の形にする。クエリは付けない
> 2. QRに入れるのは機械IDだけ。持ち主・現場・日付など変わるものは入れない
> 3. 読んだ後にどのアプリを開くかは、ハブが決める。**アプリ名をQRに入れない**
> 4. 誤り訂正はH。QRの下に人が読める文字でIDを必ず刷る
> 5. 他人の端末には何も見せない。IDだけで中身を返さない
> 6. 同じドメインに寄せる場合は、キャッシュ名とDB名にアプリごとの接頭辞を付け、
>    **自分の接頭辞のキャッシュだけを消す**こと（他アプリのキャッシュを消さない）
> 7. すでにQRを使っている場合は、現状の書式をまず報告すること。差し替えは別途指示する

## なぜこの形にしたか（経緯）

- 当初の案は `TERRA|<アプリ名>|<種別>|<中身>` というテキスト形式だった。
  しかし「**重機1台にQR1つで、すべてのアプリが動く**」という要件が出たため、
  アプリ名をQRに入れる形は成立しない。**破棄してURL形式に変えた**
- テキストだけのQRは、カメラが文字を表示するだけでアプリが開かない。
  読んだら次の動作につながらないQRは価値がない（現場の指摘）
- 検収側で検討した「会社名のQR」「トラックのQR」も、
  **同じ考え方（変わらないものだけ）**で、この規格の `c` と `m` に収まる
