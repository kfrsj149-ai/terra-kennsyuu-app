# 構想：検収データを工場へ渡す（QR受け渡し／便の概念）

> 2026-10-01 神田との議論の記録（同日中に追記あり）。**車番の必須化以外はまだ実装していない。** 初版リリース後に着手するか判断する。
> 値付けはこの絵が固まってから行う（機能が決まれば価格は決まる、という順序）。

---

## 1. なぜやるか

競合（Log Counter Plus 等）は**カウンター**である。本数を数えて材積を出すだけ。
ここで勝負しても真似される。

勝てるのは**数えた後**。検収が本当に生んでいるのは数字ではなく、
「この材をこの日この量で渡した」という**証憑**であり、その受け渡しである。

一言でいうと **「本数を数える道具」から「伝票と証憑を渡す道具」へ。**

### 決定的な着想（神田）

**受け取る側（工場）の痛みを、受け取る側にコストゼロで取り除く。**

工場の本当の苦痛は材積計算ではなく、**汚い手書き伝票の転記**である。
パートが1枚打ち込むのに数分。1日30台なら数時間。人ひとり分の人件費。

- 積む側（素材生産者・運転手）→ 課金する
- 受け取る側（工場）→ **無料**

市場の片側を無料で握る形。両側が揃うほど双方の価値が上がる（ネットワーク効果）。

## 2. 仕組み（2026-10-01 時点の設計）

### 流れ

1. 会社が**会社名とQRを印刷した紙の伝票**を用意し、運転手に持たせる
   （自社便・外注便の両方で使う）
2. 運転手が山で積みながらTERRAで計測する。**圏外でよい**（従来どおり端末内に保存）
3. 工場に着くと電波が入るので、**そこで自動的にアップロード**される
   （工場は人里にあるため電波は確実にある）
4. 運転手が紙の伝票を工場に渡す
5. 工場が**自社のIDでログインした端末**でQRを読む
6. その会社から自工場宛の**未受領の便**が一覧で出る。車番を選ぶ
7. 中身が表示され、**工場のシステムの取込形式でCSVが落ちる**

### 紙のQR：車番を入れるかどうかは選べるようにする（2026-10-01 確定）

| 運用 | QRに入れるもの | 理由 |
| --- | --- | --- |
| 自社便がメイン | 会社名 + 車番 | 自分で全部配れる。車ごとの管理もできる |
| 運送会社に頼む | 会社名だけ | どの車が来るか分からない。運送会社に同じ紙を束で持たせる |

車番を入れない場合、車番はアプリ側のデータに入っているので工場側の一覧に表示される。
工場は目の前のトラックの車番を押すだけでよい。

### トラック本体に貼るQR：中身は「トラックID」（会社ではない）

当初「トラックに会社のQRを貼る」案を出したが、外注トラックは複数社の荷を運ぶため、
請け負っている会社ぶんのQRを全部貼ることになり成立しない（却下）。

**貼るのは「そのトラック自身のID」**にすれば成立する。

- どの会社の荷を積んでいても関係ない。荷の中身は計測した時点でTERRAが知っている
- **1台につき1枚**。外注でも1枚。ナンバーを変えたら貼り替えるだけ
- 工場はトラックのQRを読むだけでよく、**紙すら要らない**

つまり役割が分かれる。

- **紙のQR** … まだTERRAを知らない工場への入口
- **トラックのステッカー** … すでに使っている工場への近道

そして**走る広告**になる。日本中の丸太トラックに同じQRが貼ってある状態を目指す。

### 「最新1件」ではなく「未受領トレイ」にする

ピストン輸送（同じ車が午前・午後に2回運ぶ）で、
工場が午前便を処理する前に午後便が着くと、午前便が埋もれる。

**未受領の便は消さずに残し、工場が「受領」を押して初めて消える。**
一番新しい便を大きく出すのは良いが、それだけを見せてはいけない。

結果として工場側に「今日まだ処理していない荷が一目で分かる」という
追加の価値が生まれる。むしろこちらが本体かもしれない。

### 現場で必ず起きること

- **QRは泥と雨で必ず読めなくなる。**
  → QRの下に「杉澤林業」と**人間が読める文字**を必ず印刷する。
     読めなければ工場が手で検索できるようにする。これを省くと
     「1回読めなかった」だけで使えない道具と判定される
- **車番の選び忘れ。**
  → 車番を**必須項目に昇格**させる（現在は任意）。
     車番が入っていない便は工場側で特定できない
- **データがまだ上がっていない。**
  → 工場側に「まだ届いていません」と正直に出す。
     黙って空のリストを見せると「壊れている」と判断される

### 初回体験（2026-10-01 に前の設計を訂正）

当初「ログインした端末でだけ見せる」としたが、**それでは初回の体験が作れない**。
工場は登録などしてくれない。訂正して次のようにする。

- **1回目** … QRを読む → 「○○から荷物が来ています。工場を選んでください」→
  選ぶだけ（登録なし・メールなし）→ **中身が出る・CSVが落ちる**
- **2回目以降** … その端末が覚えているので、読むだけで出る

ログインではなく「最初に工場を1回選ぶだけ」。
それでも**その会社から自分の工場宛の便しか見えない**ので他社の荷は漏れない。

**「何これ」から「うわ出た」までを10秒以内**に収める。ここで登録画面を出したら終わる。

### セキュリティの一線

**他人の取引量が見える状態を作らない。**

工場の画面には自分宛だけ、素材生産者の画面には自分の荷だけ。
外に出す統計は匿名化してから。設計の最初から分けておかないと後から直せない。

将来の集計機能も同様。**他人の取引量が見える状態を作らない。**
工場の画面には自分宛だけ、素材生産者の画面には自分の荷だけ。
外に出す統計は匿名化してから。設計の最初から分けておかないと後から直せない。

## 3. 構造上の発見：「便」という単位が足りない

**1台のトラックが2つ以上の現場を回るのは林業では当たり前。**
（班が複数ある会社、前の現場の片付けが終わらないうちに次の山に入る、など）

現在のアプリは **1伝票 = 1現場・1樹種・1規格長**。
1台ぶんをひとまとめにする単位が存在しない。

必要なのは **「便」**（1回の運搬）という束ねる箱。

```
便（518で ○○製材 へ・10/1 14:20）
  ├ A山 / スギ / 4m / 10本 / 1.800m³
  └ B山 / スギ / 3m /  8本 / 1.418m³
  合計 18本 3.218m³
```

- 工場が受け取る単位は「便」
- 現場名はQRに入れない。**便の中身に入る**ので、QRは入口を指すだけでよい
- 計測画面に「現場を変えて続ける」を1つ足し、終わったら便ごと出す

### 便の中身の切り替えはタブにする（2026-10-01 確定）

4mと2mを積み合わせる（積載効率のため）のは普通にある。
ただし**1画面に両方の径級ボタンを同時に出すのは禁止**。
径級グリッドは「4m材の14cm」として出ているので、2m材を混ぜると
炎天下・手袋でどちらを押しているか分からなくなる。最悪の誤入力。

```
[ スギ 4m ] [ スギ 2m ] [ + ]   ← 上にタブ。グリッドは常に1つだけ
  18cm 5本   20cm 3本
この規格：10本 1.8m³ / 便の合計：28本 4.6m³
```

タブを押すだけで切り替わる。測り直しも画面を閉じることもない。
「ひとつながりの作業でやりたい」という要件は満たしつつ、押し間違いはゼロにできる。
種類数に上限は設けない（タブなので増えても画面は壊れない）。
現場も樹種も規格長も、タブごとに別々に持てる。

既存の計測画面・JAS材積計算・オフライン保存は壊れない。
**いまの伝票が「便の中身1つ」になるだけ**だが、上に一段箱を足す作業なので小さくはない。

### 書類（合法性証明）との相性がここで効く

1台2現場なら、**伐採届も合法木材証明書も2現場ぶん必要**になる。
紙なら2枚コピーして運転手に持たせる。3現場なら3枚。

アプリなら便を開けば現場ごとに書類がぶら下がっている。工場は何もしなくてよい。
**現場が増えるほど紙との差が開く。** ここが売り文句になる。

## 4. 書類まわり（現場に紐づく静的情報）

書類は丸太1本ごとではなく**「山（現場）に1セット」**。
現場マスタ（いまは単なる文字列）に以下をぶら下げる。

| 現場に持たせるもの |
| --- |
| 事業者の認定番号 |
| 伐採届の番号・PDF/写真 |
| 合法木材証明書 |
| 山の通称・住所・林班 |
| 納入先ごとの受入開始届（提出済み／未提出） |

事務所が一度入れれば、現場の人は何もしなくていい。
「共有ファイルで管理すればいいのに誰もやらない」のは**置き場所がないから**であり、
検収アプリの中に置けば嫌でも揃う。

受入開始届は「現場 × 納入先」で1回必要。
**未提出なら計測開始時に警告**できる。
なお**書類が要るのは新しい現場の1台目だけ**。工場側に「この現場の書類は受領済み」を
持たせて、2台目以降は書類欄を畳む。

### 現場と伐採届は1対1ではない（2026-10-01 現場確認）

民有林では、1つの「現場」が所有者5〜6人分にまたがり、**伐採届が8枚**ということが普通にある。

- **混ぜる会社**（杉澤林業）… 全部まとめて1つの届出で出す。現場だけ選ぶ
- **分ける会社** … 物理的に分けて管理している。「山田さんの伐採届5133の山から出た4m」まで選ぶ

```
現場「本谷」
  ├ 伐採届 5133（山田さん）
  ├ 伐採届 5134（佐藤さん）
  └ …… 全部で8枚
```

**現場の下に伐採届をぶら下げ、選ぶのは任意にする。** 同じアプリで両方の運用に対応できる。

また、古い現場で余った丸太を新しい現場の伐採許可に足して出すことは実務上ある
（自然物なのでぴったりにはならない）。
**アプリは数が合うかどうかの判定をしない。** それは行政の仕事であって道具の仕事ではない。
厳密にしすぎると現場で使われなくなる。

## 5. 関門（楽観してはいけない点）

### 関門1：CSVが落ちても工場は楽にならない

工場には自社の販売管理システムがある。
**CSVをダウンロードしても取込形式が合わなければ、結局手入力になる。**

→ **工場ごとの取込フォーマットに合わせてCSVを出す**（列順・文字コード・
　 ヘッダー有無・径級の書き方を工場側の管理画面で設定）。

地味だが**ここが本丸**。競合は絶対にここまでやらない。
そして一度合わせた工場は離れられない。資本のある会社が真似したがらない堀はここ。

### 関門2：オンライン化はアーキテクチャの転換

現在のTERRAは完全オフライン、データは端末内のみ。
工場がQRで見るには**データがサーバーに上がっている必要がある**。

- データベースが要る（現在はStripe用の `/api/*` だけ）
- 運用責任が跳ね上がる。落ちたら他人の業務が止まる
- 無料の工場アカウントが増えるとサーバー費だけが先に増える

ただし設計は素直。山では従来どおりオフラインで溜め、工場に着いてから上げる。
**オフラインファーストの思想は壊れない。**

### 関門3：「誰が数えるか」で設計が変わる

- **運転手が数える** → データが荷物と一緒に移動する。問題なし（本線）
- **山の人が数える** → データと荷物が別経路。トラックが先に着くと工場に何もない

運転手から「作ってくれ」と言われた経緯からすると運転手が数えるのが本線。
ただし両方起こるので、工場側には「まだ届いていません」と正直に出す。

## 5.5 どうやって工場に広めるか

**運転手は絶対にプロモーションしない。** 「QRで読めばインストール不要ですよ」などと
説明してくれるはずがない。

答えは **「紙が営業する」**。伝票にこう印刷しておく。

```
┌────────────────────────────────┐
│  このQRをスマホで読むと、この荷物の明細が   │
│  そのまま表に出ます。登録もアプリも不要です。 │
│         [ QR ]   杉澤林業                │
└────────────────────────────────┘
```

運転手は紙を渡すだけでよい。事務の人が「何これ」と読む。それで終わり。
ヤマトの送り状も、誰も説明していないのに全国で運用が回っているのと同じ理屈。

### 導入の最大の敵は、工場の事務の人

「転記の手間がなくなります」と言った瞬間、**その人は自分の仕事が消える話として聞く**。
本人は冗談のつもりでも本能的に抵抗するし、現場で止めるのは社長ではなくその人。

売り文句を変えること。

- ❌ 転記の手間がなくなります
- ✅ **転記の打ち間違いがなくなります**

数字が合わなくて電話で確認する、あのやりとりが消える、と言う。
**仕事を奪う話ではなく、嫌な仕事が消える話にする。**

## 6. 売る順序

**工場1社を落とす。** 組合や市売市場を口説くより速い。

工場1社には素材生産者が10〜30社ぶら下がっている。
その工場が「TERRAで来る荷は楽だから使ってくれ」と言い始めたら、
**向こうから勝手に広がる。**

汎用品を作ってから売るのではなく、**1社に刺さるものを作ってから横に広げる。**

### 最初に調べること

いま納めている工場で、手書き伝票を打ち込んでいるところを1社特定する。

- 誰が打ち込んでいるか
- 1日何枚か、1枚何分か
- **使っている販売管理システムは何か**（これでCSVの形が決まる）

## 6.5 ロックインの本命：取引の「正本」を握る

いま丸太の数字の正本は紙の伝票である。揉めたら紙を見る。だから紙が主役。

ここで**工場側が自分の検収結果をTERRAに入れられる**ようにすると、

```
杉澤林業の検収   18本  3.218m³
○○製材の検収    18本  3.201m³   ← 差 0.017m³
```

両方の数字が1画面に並ぶ。
いまは「数が合わない → 電話 → 紙を探す → 言った言わない」。それが消える。工場も楽になる。

そして両者が**「TERRAの数字で精算しよう」**と言い出した瞬間、正本が紙からTERRAに移る。
**こうなると片方だけではやめられない。** 精算の根拠がなくなるため。これがロックインの正体。
ヤマトの追跡番号が最終証拠になるのと同じ構造。

**実装は小さい。** 工場側の画面に数字を入れる欄を1つ足すだけ。差は勝手に出る。
機能としては地味だが、効果は全機能の中で最大。**これが本命。**

### その先（順番を守ること）

| | 時期 | 中身 |
| --- | --- | --- |
| ① 正本を握る | すぐ | 上記 |
| ② 相場が見える | 2〜3年後 | 匿名化した集計。**日本で唯一、丸太の実流通が見える場所**になる。市場も組合も自分を通った分しか見えない。ただし信頼を壊すリスクも最大なので匿名化と同意が絶対条件 |
| ③ 空車マッチング | 別事業 | 山へ行って積んで降ろして**空で帰る**問題。TERRAは「どの車がいつどこにいたか」を知っている。ただし別アプリにしないと共倒れする |

②は①が回ってから。順番を間違えると信用が吹き飛ぶ。

## 7. 「物流を牛耳る」の正確な意味

牛耳るのは物流そのものではなく、**取引の数字が生まれる瞬間**。

丸太を動かすのは我々ではない。しかし
「何が・どこから・どこへ・どれだけ」が全部そこを通るなら実質同じ力を持つ。

誰がどれだけ出しているか、どの樹種が動いているか、相場がどう動いているかが見える。
ただし **5章のセキュリティの一線**を守ること。

## 10. 納入枠（組合の枠）と事務所端末（2026-10-01 追記・神田さん）

### 現場の実態

- 組合（ノースジャパン素材流通協同組合）を通して、工場（例：秋田プライウッド）に
  「今月、カラマツの合板材を400m³納めてよい」という**枠**をもらう
- 枠には「納入希望枠」と「納入可能枠」があるが、**使うのは納入可能枠だけ**（希望枠は忘れてよい。神田さん）
- **FAXで届く。** 納入できる**日付・曜日・時間帯（朝何時〜夜何時）**が書いてある
- 事務所がFAXをコピーして、運転手に**紙で渡している。** 外注の運送会社にも同じ

### 神田さんの希望

1. **事務所用の端末**を作る。枠の情報を、事務所が入力する
2. 外注の運送会社や運転手が、**いつでも見られる**
3. （できれば）工場に**今何台目が来て、何m³入れたか**が分かる。**カウントダウン**（あと30m³、あと480m³）

### 見立て

- これで、**事務所を真ん中に置く3者の構造**（運転手／事務所／工場）になる。工場への受け渡しの構想と、同じサーバーを使う
- 必要なデータ（枠カード）：工場、材種、数量、期間、曜日、時間帯、備考、**FAXの写真（原本）**
- 枠カードは、運転手のセットアップの**「納入先」の選択に載せる。** 選んだ枠に、便の材積が積み上がる
- 小さいが効く機能：枠カードの曜日・時間帯から、**「今は荷下ろしの時間内か」を自動で表示**する
  （例：「今は荷下ろしできます」「次は明日6:00から」）

### 段階（案）

0. **サーバーなし。** 事務所が枠カードを入力し、LINEなどで共有する（Web Share）。
   集計は、運転手が今までどおり共有するCSVを、事務所が取り込んで行う
1. **サーバーあり。** 枠カードの共有、便のアップロード、カウントダウン

### 確定したこと（神田さん・2026-10-01）

1. **使う枠は「納入可能枠」だけ。** カウントダウンは、納入可能枠から引いていく
2. **枠から引く数字は、「工場の検収値があれば工場の値」「なければこちらの値（伝票どおり）」の順。**
   工場が測り直す所もあれば、こちらの伝票の量をそのまま使ってくれる所もある（工場ごとに違う）
3. **進捗は、運転手と運送会社に全部見せる。** 見せないと、あと何台か分からない。
   （他の素材生産者のデータは見せない。セキュリティの一線は変わらない）

設計への影響：

- 便ごとに、**こちらの値**と**工場の値（あれば）**を持つ。枠の消化は「工場の値があればそれ、なければこちら」
- 工場の値が**まだ出ていない便は、「確定」と区別して表示する**（例：確定 320m³＋工場の検収待ち 30m³）。
  工場が測り直す所では、確定と見込みのずれが出るため
- 工場ごとに「測り直す／伝票どおり」の設定を持つ（案）

### 臨時のお知らせ（新しい要望・神田さん）

FAXやメールで、枠とは別に、次のような連絡が来る。**運転手にも共有する必要がある。**

- 片付けをするので、明日は納入できません
- 近隣で道路工事があるので、何日から何日までは**第1土場に入場できません。第3土場の係員に従ってください**

設計：

- **「お知らせ」カード**：工場（または**土場**）、期間、種類（納入不可／入場制限／案内）、内容、FAX・メールの写真
- 運転手の画面の**いちばん上に、赤い帯で出す**（納入不可・入場制限）。期限が切れたら自動で畳む
- **「今は荷下ろしできるか」の表示に、お知らせを反映する。** 窓の時間内でも、お知らせで納入不可なら「できません」と出す
- 工場には**複数の土場**がある。お知らせは、工場全体にも、特定の土場にも付けられるようにする
- **古い情報を、正直に出す。** 「最終更新 10/1 8:12」を表示し、圏外のときは
  「通信がないため、最新でない可能性があります」と出す。古い情報で空振りすると、運転手の1日が無駄になる
- 知らせ方：段階0はLINEの共有。段階1はアプリの帯。**プッシュ通知は、Androidは使える。iPhoneはホーム画面に
  追加したアプリに限られ、確実ではない**ので、LINEと併用する

### 工場の数字はどこから来るか（神田さん・2026-10-01）

工場の数字は、3つの段階を経て、事務所に戻ってくる。

| 段階 | 数字 | 来るもの |
| --- | --- | --- |
| ① 見込み | こちらの検収値 | 自分たちの伝票・CSV |
| ② 工場の検収 | 工場の検収値 | FAX、戻ってきた伝票 |
| ③ **最終確定** | **月末の精算書の値** | 月末に工場から届く。**規格外などをはねた後の数字** |

- **本当に確定した値は、月末の精算書。** 枠の消化は、①→②→③の順に、新しい段階の数字で置き換えていく
- 事務所は今、**これを全部エクセルに手入力している**（神田さんの話。事務員の負担が大きい）
- 要望：**精算書を、事務所の端末、または事務員のスマホで読み取り（OCR）して、事務所用の端末にデータが入る**
- 読み取った数字を、こちらの検収値と**突き合わせ**、差（規格外のはね）を、便ごと・径級ごとに出す。
  **これが、事務員にとって一番の価値になる可能性がある。** 手入力が消える。仕事を奪う話ではなく、嫌な作業が消える話にする

技術メモ：

- **自動で確定させない。** 読み取り結果は、**元の写真と並べた確認画面**で、人が確かめてから登録する（お金に関わる数字のため）
- 日本語の表は、端末内で動く従来型のOCRが苦手。視覚を持つAIのほうが精度は高いが、
  **サーバーが要る・読み取りごとに費用がかかる・取引の情報を外部のサービスに送る**
  （プライバシーポリシーへの明記が要る）
- **精算書がPDFやExcelで届くなら、読み取りは不要で、取り込むだけ**で済む。まず形式を確認する
- 工場ごとに精算書の形式が違うはず。1工場ずつ合わせる作業になる（工場ごとのCSV形式と同じ種類の泥臭さ）
- 書き出しは、事務所が今使っているエクセルの形に合わせる。合わせないと、結局手で打ち直すことになる
- 事務所の人は、スマホで写真を撮って、事務所用端末（PC）に取り込む形でもよい（スマホとPCの同期にはサーバーが要る。
  サーバーなしなら、写真やPDFのファイルを、PCで読み込む）

### 2026-10-01 [log-truck-volume-app]
- 変更内容：差別化の方向を「計算の正確さ」から**「検収データを工場へ渡すこと」**に定めた。
  QR（会社のみ）を印刷した紙の伝票 → 工場がログイン端末で読む → 未受領の便が一覧 →

- 他プロジェクトへの示唆：**書類やデータの受け渡しがある業務アプリでは、
  「作る側」だけでなく「受け取る側」を無料で取り込めないかを必ず検討すること。**
  受け取る側は人数が少なく、痛みが大きく、押さえると作る側が自動的に集まる。
  なお受け渡しにQRを使う場合、QRには**変わらないもの（会社）だけ**を入れ、
  変わるもの（車番・日時・現場）はデータ側に置くこと。
  QRに可変情報を入れると、印刷物の刷り直しという運用コストが発生して破綻する。
