# 引き継ぎ：機械まわりを免税軽油PWAに集約する

> 2026-10-01。丸太検収（LOG-RA）のセッションで、神田さんと議論した内容を引き継ぐ。
> **このファイル1つで読めるように書いた。** 他のファイルは参照しなくてよい。
> コードを変えてよいのは、設計をすり合わせた後。まず読んで、末尾の「返してほしいもの」に答えてほしい。
> 免税軽油PWA・日報PWAの現状は、それぞれのClaudeの報告で把握済み。ここには繰り返さない。

## 1. 決定（神田さん）

1. **日報と点検を、免税軽油PWAに1つにまとめる。** 別のアプリにしない
2. 機械のQRを**1回読むだけで、1日の記録（点検・給油・作業内容）がひと続きで済む**
3. **事務所のPC側（office-dashboard）は必須。** 免税軽油の申請データの集計と書類の作成はPCで行う。日報・点検の閲覧もここに載せる
4. 日報は**売る**。まとめたアプリの契約（Stripe）に含める
5. **日報PWA（NIPPO-RA）は、コードもデータも捨てる。** 実データはテストだけだった。
   ただし**設計思想・判断・却下された案・修正の履歴は引き継ぐ**（日報のClaudeに引き継ぎ文書を作らせ、あなたに渡す。**それを最初に読むこと**）
6. **丸太検収は統合しない**（別のアプリのまま）
7. **名前は未決定。後で検討する。** 作業中は「機械まわりアプリ」と呼び、コードや画面の名前を勝手に変えない。
   （参考：NIPPO-RA＝ニッポーラは、TERRA TXの起源のアプリの名前。提案は「コードネーム＋製品名は『TERRA＋用途』」の二層）

## 2. なぜ1つにまとめるか（神田さんの現場判断）

別々のアプリだと、同じ機械のQRを3回読むことになる。**現場では使われなくなる。**
同じ機械・同じ人・同じ日の入力は、1回で済ませたい。

特に、**作業内容と作業時間は、免税軽油の申請データと日報の両方に使える「1回の入力」**になる。これが一番強い理由。

## 3. 想定する流れ（神田さんの案）

1. 機械のQRを読む（作業員・機体の選択は飛ばす。今の免税軽油のQRと同じ動き）
2. 「今日は給油しましたか？」 → はい → アワーメーターの読み取り → 給油量の入力
3. 作業内容と作業時間が表示される（アワーメーターの差分から出せるはず）
4. 点検記録を作る

**未確定：QRを読むのは朝か夕方か。** 点検は始業前が通例（要確認）で、給油や作業内容は終わった後になりやすい。
案：固定の順番にせず、**「今日この機械で、まだ終わっていないこと」を出して、次を促す。**
朝に読めば点検が先、夕方に読めば作業内容が先に出る。順番は強制しない。

## 4. QR規格（確定。要点）

- **URL：`https://<自前のドメイン>/<ID>`。** 案は `m.terra-tx-jp.com`。**ドメインは未決定。最初の印刷の前に決める。**
  QRに入るのはホスト名なので、**刷ったら、そのDNSは残し続ける**
- **IDは、会社内で一意の8文字のランダム。** 意味を持たせない。使う文字は `0123456789ABCDEFGHJKMNPQRSTVWXYZ`（紛らわしい I L O U を除く）。
  各機械に「QRのID」の欄を足す。**全社共通の機械台帳は要らない**
  （現場端末は事務所が招待して登録した端末で、自分の会社を知っているため、IDだけで機械を引ける。**報告からの推測。要確認**）
- **ハブは不要。** 統合したアプリ自身が、QRの宛先になる
- **免税軽油のQRは、まだ1台も貼っていない。** 既存の `/scan?machine_id=…` との互換は気にしなくてよい（残してもよい）
- **誤り訂正はH。** QRの下に、人が読めるIDを必ず刷る（読めない時の最後の手段）。マットで刷る。余白は周囲に4マス分

### QRの絶対ルール

1. **QRには「変わらないもの」だけを入れる。** 持ち主・現場・日付を入れない。
   実測：34バイトのURLは33マス四方、日本語入りの106バイトは53マス四方。**詰めるほど汚れに弱い**
2. **QRを読んでも、他人の端末には何も見せない。** QRにはIDしか入っていない。IDだけで中身を返してはいけない
3. **QRのURLは永久に使う。** `vercel.app` のような借り物のドメインを刷らない

## 5. 守ってほしい原則（TERRA共通）

- **Service Worker：「自分以外のキャッシュを全部消す」処理が、3つのアプリ全部にあった**（検収・免税軽油・日報）。
  今は別ドメインなので無害。**新しく書く部分（点検など）では、最初から「自分の接頭辞のキャッシュだけ消す」書き方にする**
- **行政に出す書類を作らない（保管と表示だけ）。** 免税軽油の開発理念「行政書士法に抵触しうる機能は実装しない」を、TERRA全体の方針にする案。
  法的な線引きは断定できないので、必要なら専門家に確認する
- **サーバー側DBを持つアプリは、StripeのWebhookでDBにサブスク状態を保存する**（免税軽油はすでにそうしている。そのまま）
- **同じ結果に到達する操作を2つ作らない。** 片方は使われず、誤爆の入口として残る

### 丸太検収の現場テストから得た教訓（手袋・炎天下・老眼の現場で使うUI）

1. **スクロールさせない。** 1画面に収める。収めるためなら、ボタンは48pxまで詰めてよい（指の腹はおよそ45px）。
   画面の高さはバナー・キーボード・回転で変わるので、`ResizeObserver` で測り直す
2. **文字とボタンの大きさを、標準／大／特大から選べる**ようにする。1つのCSS変数で全体が連動する形にする。
   ただし要約まで拡大すると折り返して主役の表が押し出されるので、拡大するものと、しないものを分ける
3. **危険な長押しを作らない。** 長押しを複数の場所に割り当てるなら、判定時間を揃える（2秒）。
   計測中に画面いっぱいのダイアログを出さない
4. **取り消しは消さず、取り消し線で残す。**
5. **作業中は、余計な帯（アプリバー・バナー）を隠す。** 画面を稼ぐ
6. 炎天下では、面の色だけでは境目が飛ぶ。**輪郭を濃くする**。色は「濃い×薄い」にする
7. **山からスマホだけで直して試せる仕組み**を入れる（配信中の版を問い合わせ、変わっていればキャッシュを捨てて読み直す）。
   **作業中は、絶対に自動でリロードしない**

## 6. 設計で決めたいこと（コードを知っているあなたに、見解と提案がほしい）

1. **1日の記録の単位。** 「機械×日」を1つのまとまりにして、点検・給油・作業内容の完了状態を持つ案。
   既存の `refuelLogs`（1給油=1レコード）との関係
2. **作業時間。** アワーメーターの差分から出せるか。前回の読み取りがない日、複数日またぎ、アナログメーター（手入力）の扱い
3. **日報の項目。** 現場・天候・路面・風速・参加作業員・稼働時間帯（日報PWAより）。免税軽油の「作業員・機体」の持ち方との整合
4. **権限。** 日報側はフラット（許可済みなら誰でも読める）だった。統合後は、
   作業員は自分の記録、事務所は全部、点検の異常は事務所へ通知、など
5. **「1秒完了」の理念。** ステップが増えるので、各ステップの省略・既定値・後からの入力をどうするか
6. **行政書士法。** 申請書類を「作る」のではなく、データを集めて見せる
7. **業種。** 免税軽油は**全産業**の機械が対象。土台は業種に寄せず、日報・点検は林業向けの項目から始め、
   業種ごとに項目を切り替えられる形を意識する。**他の業種の作り込みは、需要が見えてから**

## 7. 進め方（案）

段階に分けて、各段階で使える状態にする。一度に作らない。**免税軽油の完成を遅らせない。**

1. QRを読む入口と、給油（今ある機能）
2. 作業内容・作業時間（日報）を、同じ流れに
3. 点検
4. 日報PWAの利用者の移行（実データはテストだけなので、移行するデータはない）
